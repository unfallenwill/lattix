# M0.5 目标：架构硬化

> 状态：拟定
> 关系：在 PRD v1 的 M0（架构立形）已完成 + M1（功能扩展）开始前，集中偿还 3 笔关键债。
> 范围：3 个工作项，全部不引入新字段类型 / 新视图 / 新协议形态——只把"已经存在但没收尾"的基础设施做完。

---

## 为什么是这 3 件

| | 性质 | 不做的代价 |
|---|---|---|
| #1 客户端重连后订阅丢失 | **bug** | 重连功能形同虚设；未来实时联动越完善，bug 越扎眼 |
| #2 引入 FieldTypeManifest | **地基** | 后续 formula/link/lookup/select 多选都要踩这一层，越晚做迁移越贵 |
| #3 类型化客户端 SDK + 收敛 Router 注册 | **纪律** | 每加一个协议方法就多踩一次"四处手维护字符串"的坑 |

**推荐顺序**：#1 → #3 → #2。理由：#1 是 bug 先修；#3 改动机械、给后续工作铺路；#2 在 #3 完成后做，新增的 `field.types.list` 协议方法立刻享受类型化客户端。

## #1 修客户端重连后的订阅丢失

### 现象

`LattixConnection` 重连成功后，原来订阅的 channel 不会自动重新 `subscribe`。结果是断网恢复后 TUI 看起来 connected，但所有 push 都收不到，数据静默陈旧，直到用户手动切表。

### 行为标准

| # | 场景 | 期望 |
|---|---|---|
| B1 | TUI 已订阅 `table.t1.records`，强杀 Core 并立即重启 | 重连成功后 5 秒内重新收到 record.* push，无需用户切表 |
| B2 | 拔网线 10 秒后插回 | 同 B1 |
| B3 | 重连期间用户按 Enter 编辑 cell | 不立即 `not connected` 报错；500 ms 窗口内重发；超时再报错 |
| B4 | 用户主动 `close()` | 不触发任何重连或重订阅 |
| B5 | 端口永久不可达 | 重试遵守现有 backoff，无 unhandled rejection |

### 工程标准

- E1 新增 `client/__tests__/reconnect-resubscribe.test.ts`：fake server close + reopen，断言 subscribe 帧被重发、push 送达 handler
- E2 新增"短窗口排队"测试覆盖 B3
- E3 `client/src/connection.ts` 行覆盖率 ≥75%
- E4 `npm run check` 全绿
- E5 现有测试 0 回归

### 不在范围

- ❌ outbox / 持久化未送达请求
- ❌ 改 push 的传递语义
- ❌ 改服务端 PeerState
- ❌ UI 改动（StatusBar 现有的 reconnecting 状态够用）

### Done 的硬证据

- [ ] B1 手动复现一次：杀 Core，看 TUI 是否自动恢复 push
- [ ] E1/E2 测试都新增且绿
- [ ] commit message 说清楚 fix 的 bug 是什么

## #2 引入 FieldTypeManifest + 算子声明

### 现状

字段类型能力散在 4 层（protocol/shared/core/tui），且没有"算子"维度。`records.ts` 的 sort key 硬编码 `['updated_at','created_at']`，正是因为缺这层元数据。formula/link/lookup 都需要这个维度。

### 行为标准

| # | 场景 | 期望 |
|---|---|---|
| B1 | 调 `field.types.list` | 返回 5 个 manifest，每个含 id / displayName / category / optionsSchema(JSON Schema) / operators / storage.sqlType / icon |
| B2 | TUI 启动 | 能读到 manifest（不要求立刻改 UI 用，但 API 通了） |
| B3 | `record.list` 带 `sortBy: 'fNum'`（number） | 允许，因为 manifest 声明 `sort: 'numeric'` |
| B4 | `record.list` 带 sortBy 指向 checkbox 字段（manifest `sort: 'none'`） | 返回 `BAD_REQUEST: field type does not support sort` |
| B5 | 现有所有写入路径 | 行为完全不变 |

### 工程标准

- E1 新文件 `shared/src/field-type-manifest.ts` 定义 `FieldTypeManifest` 接口：`id / version / displayName / category / optionsSchema / valueSchema / validate / serialize / defaultValue / storage.{sqlType,indexable} / operators.{filter,sort,aggregate} / icon`
- E2 `createBuiltinFieldRegistry()` 返回 `Map<FieldType, FieldTypeManifest>`，5 种内置类型填齐
- E3 `FieldType` 静态联合类型不变（TS 检查不退化）
- E4 `protocol/methods.ts` 加 `'field.types.list'`；router 注册 handler
- E5 `core/storage/records.ts` 的 sortBy 白名单从硬编码改为查 manifest
- E6 `shared/__tests__/manifest.test.ts` 断言 5 种类型都满足 manifest 形状
- E7 `core/__tests__/field-types-list.test.ts` 走真 Router 调 `field.types.list`，断言返回 5 项且形状对
- E8 集成测：number 字段排序成功；checkbox 字段排序返回 BAD_REQUEST
- E9 `shared/field-type-manifest.ts` 行覆盖 ≥85%
- E10 `npm run check` 全绿
- E11 现有测试 0 回归

### 不在范围

- ❌ 插件加载器 / 动态发现 / plugin manifest
- ❌ TUI 的"新建字段"对话框改造
- ❌ formula / link / lookup 类型本身
- ❌ storage 多后端
- ❌ 字段 options 现有 schema 改动

### Done 的硬证据

- [ ] wscat（或测试代码）调通 `field.types.list`，返回 JSON 形状对
- [ ] grep：`core/src/storage/records.ts` 不再出现 `['updated_at','created_at']` 字面值
- [ ] E1–E11 全部 ✓

## #3 类型化客户端 SDK + 收敛 Router 注册

### 现状

两个问题，同一个本质——已经做过类型推导，没让推导成果落地：

- `client.request<T>('record.list', ...)` 每次都要手写 `as { records: RecordRow[] }`，protocol 的 zod 类型推导白做了
- `Router` 的 `METHOD_NAMES` / `PARAM_SCHEMAS` / `switch case` / Service 调用四处手维护字符串

### 行为标准

| # | 场景 | 期望 |
|---|---|---|
| B1 | TUI 的 `DataStore` | 所有 `conn.request<T>('xxx', ...)` 替换为 `client.xxx.yyy(params)`，IDE 自动补全方法名 + 参数类型 + 返回类型 |
| B2 | 写错方法名（`field.lst`） | TypeScript 编译错误 |
| B3 | 给 `record.list` 传错 params 形状 | TypeScript 编译错误 |
| B4 | 新增一个协议方法 | 仅在一处声明（method def 文件），Router 自动注册、客户端 SDK 自动有方法 |
| B5 | wscat 调用未注册方法 | 行为不变：`NOT_IMPLEMENTED` |

### 工程标准

- E1 `protocol/` 新增 method def 形式：`{ name, paramsSchema, resultSchema, summary }`，每个方法一份
- E2 `protocol/` 导出聚合类型 `AllMethods = Record<MethodName, MethodDef<any, any>>`
- E3 `core/router.ts` 改成单一注册表：`registerMethod(def, handler)`；删除 METHOD_NAMES 数组、PARAM_SCHEMAS record、switch case
- E4 `client/` 新增 `LattixClient` 类，从 method def 派生类型化方法。命名空间形如 `client.tables.list()` / `client.records.list({tableId})`
- E5 `tui/store/data-store.ts` 不再有 `this.conn.request(...)` 字面调用，全部走 `this.client.xxx()`
- E6 类型测试（`expectTypeOf` 或 `tsd`）：错误方法名 / 错误 params 形状编译失败
- E7 单测：注册表机制——注册 fake method 命中、注册重名报错、未注册返回 NOT_IMPLEMENTED
- E8 集成测：所有现有 method 端到端走一遍，行为等价
- E9 `client/` 覆盖率 ≥80%；`core/router.ts` ≥95%
- E10 dep-cruiser：`client/` 仍只依赖 `protocol/` 和 `shared/`
- E11 `npm run check` 全绿，0 回归
- E12 grep：`tui/` 下不再出现 `as { records:` / `as { tables:` 等手写断言

### 不在范围

- ❌ 改协议帧格式
- ❌ 改重连/订阅（#1）
- ❌ 引入 OpenAPI / gRPC / code-gen
- ❌ SDK 的 React hooks
- ❌ SDK 对外发布

- [ ] B2/B3 在 IDE 里肉眼可见红波浪

## 不做的事（M0.5 范围外，留给 M1+）

- 字段类型扩展：formula / link / lookup / attachment / user / multiselect
- 视图扩展：kanban / gallery / calendar
- 高级查询：data-query DSL、复杂筛选 UI
- 插件系统：plugin loader、sandbox、permissions
- Storage 多后端：DuckDB / Postgres / 内存
- 通讯协议：gRPC / REST adapter
- Schema migration runner（SQLite ALTER 迁移）
- Core 日志系统
- GridView 拆分

这些都有价值，但**都不应该排在 #1/#2/#3 前面**——前两件是"不做就在烂"，第三件是"不做后面每件事都变贵"。
